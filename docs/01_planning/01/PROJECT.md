# PROJECT.md

## Содержание

## Цель проекта

Цель проекта OrbitaMarket - разработать микросервисную платформу для продажи спутниковых продуктов с поддержкой заказов, внутреннего биллинга в геокредитах и асинхронной оплаты через брокер сообщений.

Платформа должна позволять пользователям:

- создавать счет в геокредитах;
- пополнять баланс;
- создавать заказы на спутниковые продукты;
- отслеживать статус оплаты заказа;
- получать список собственных заказов;
- просматривать текущий баланс;
- обеспечивать корректное списание средств даже при повторной доставке сообщений и параллельных операциях.

Ключевая цель системы - обеспечить надежный сценарий:

1. создание счета
2. пополнение баланса
3. создание заказа
4. асинхронная оплата
5. обновление статуса заказа

## Стейкхолдеры проекта

### Клиент платформы

Клиент платформы - пользователь, который покупает спутниковые продукты: архивные снимки, будущую съемку или мониторинг территории.

Интересы клиента:

- быстро создать заказ;
- увидеть текущий статус заказа;
- получить понятную ошибку при недостатке средств;
- быть уверенным, что средства не спишутся дважды;
- в будущем пользоваться графическим интерфейсом без ручной работы с API.

### Оператор платформы

Оператор отвечает за работоспособность сервиса, корректность заказов, стабильность оплаты и подготовку демонстрации проекта.

Интересы оператора:

- запуск всей системы одной командой через docker-compose;
- наблюдаемое поведение сервисов;
- понятные логи;
- корректная работа брокера сообщений;
- наличие документации, диаграмм и тестов;
- возможность показать демонстрационный сценарий на защите.

### Разработчик / команда сопровождения

Разработчик отвечает за реализацию, тестирование и поддержку системы.
Интересы разработчика:

- четкое разделение ответственности между микросервисами;
- отсутствие общих таблиц между сервисами;
- понятные контракты REST API и событий;
- возможность расширения проекта;
- готовая база для подключения графического интерфейса;
- наличие автотестов и отчета Allure;
- документированный анализ информационной безопасности.

## Архитектурный подход

Проект реализуется как набор микросервисов:

- API Gateway
- Payments Service
- Orders Service
- Message Broker

### API Gateway

API Gateway является единой точкой входа в систему.

Ответственность:

- принимать внешние HTTP-запросы;
- маршрутизировать /payments/ в Payments Service;
- маршрутизировать /orders/ в Orders Service;
- пробрасывать заголовок X-User-Id;
- не хранить состояние заказов и балансов;
- не содержать бизнес-логику.

### Payments Service

Payments Service отвечает за биллинг в геокредитах.

Ответственность:

- создание счета;
- контроль уникальности счета на пользователя;
- пополнение счета;
- получение баланса;
- списание геокредитов по событию OrderPaymentRequested;
- идемпотентность списания по order_id;
- публикация результата оплаты:OrderPaymentCompleted;
- OrderPaymentFailed.

### Orders Service

Orders Service отвечает за жизненный цикл заказа.

Ответственность:

- создание заказа;
- валидация типа продукта и payload;
- сохранение заказа;
- перевод заказа в статус PAYMENT_PENDING;
- публикация события OrderPaymentRequested;
- получение результата оплаты;
- перевод заказа в PAID или PAYMENT_FAILED;
- получение списка заказов пользователя;
- получение конкретного заказа.

### Message Broker

Брокер сообщений используется для асинхронного взаимодействия между сервисами.
