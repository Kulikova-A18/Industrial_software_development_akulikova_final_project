# ROADMAP.md

В данном документе описаны этапы.

## Этап 1. Подготовка проекта и архитектуры

Период: 10 июня - 12 июня

Цель этапа: Подготовить базовую структуру проекта, определить архитектуру, стек технологий и контракты взаимодействия сервисов.

Задачи:

- Создать основной репозиторий проекта OrbitaMarket.
- Создать структуру микросервисов:
  - api-gateway;
  - orders-service;
  - payments-service.
- Выбрать стек:
  - Java;
  - Spring Boot;
  - Spring Web;
  - Spring Data JPA;
  - PostgreSQL;
  - Kafka или RabbitMQ;
  - VDocker Compose;
  - Flyway или Liquibase;
  - JUnit;
  - RestAssured;
  - Allure.
- Описать границы сервисов.
- Подготовить файл PROJECT.md.
- Зафиксировать формат идентификации пользователя:
  - заголовок X-User-Id.

Результат этапа: После завершения этапа должна быть создана начальная структура проекта и зафиксированы основные архитектурные решения.

## Этап 2. Реализация Payments Service

Период: 13 июня - 17 июня

Цель этапа: Реализовать сервис платежей, который управляет счетом пользователя и выполняет списание геокредитов.

Задачи:

- Создать приложение payments-service.
- Настроить подключение к Payments DB.
- Создать миграции базы данных.
- Реализовать таблицу accounts.
- Реализовать таблицу payment_operations или inbox_events для идемпотентности.
- Реализовать REST API:
  - POST /api/v1/payments/accounts;
  - POST /api/v1/payments/accounts/top-up;
  - GET /api/v1/payments/accounts/balance.
- Реализовать валидацию:
  - наличие X-User-Id;
  - сумма пополнения больше нуля;
  - существование счета.
- Реализовать единый формат ошибок.
- Реализовать защиту от конкурентных изменений баланса.
- Реализовать обработку события OrderPaymentRequested.
- Реализовать публикацию событий:
  - OrderPaymentCompleted;
  - OrderPaymentFailed.

Результат этапа: Payments Service должен уметь создавать счет, пополнять баланс, возвращать баланс и списывать средства за заказ без повторного списания при дубликате события.

## Этап 3. Реализация Orders Service

Период: 18 июня - 23 июня

Цель этапа: Реализовать сервис заказов, который создает заказы на спутниковые продукты и обновляет их статус после оплаты.

Задачи:

- Создать приложение orders-service.
- Настроить подключение к Orders DB.
- Создать миграции базы данных.
- Реализовать таблицу orders.
- Реализовать таблицу outbox_events.
- Реализовать таблицу inbox_events для обработки результатов оплаты.
- Реализовать REST API:
  - POST /api/v1/orders/orders;
  - GET /api/v1/orders/orders;
  - GET /api/v1/orders/orders/{order_id}.
- Реализовать создание заказа типа ARCHIVE.
- Реализовать валидацию:
  - наличие X-User-Id;
  - price > 0;
  - product_type = ARCHIVE;
  - обязательные поля payload.
- Реализовать статусы:
  - CREATED;
  - PAYMENT_PENDING;
  - PAID;
  - PAYMENT_FAILED;
  - REJECTED.
- Реализовать публикацию события OrderPaymentRequested.
- Реализовать обработку событий:
  - OrderPaymentCompleted;
  - OrderPaymentFailed.
- Реализовать сохранение failure_reason.

Результат этапа: Orders Service должен создавать заказ, отправлять событие на оплату и обновлять статус заказа после ответа от Payments Service.

## Этап 4. Настройка брокера и асинхронного взаимодействия

Период: 24 июня - 27 июня

Цель этапа: Обеспечить асинхронную оплату через брокер сообщений и гарантировать корректную обработку повторных сообщений.

Задачи:

- Добавить брокер сообщений в docker-compose.
- Создать топики или очереди:
  - order-payment-requested;
  - order-payment-completed;
  - order-payment-failed.
- Настроить producer в Orders Service.
- Настроить consumer в Payments Service.
- Настроить producer в Payments Service.
- Настроить consumer в Orders Service.
- Реализовать Transactional Outbox в Orders Service.
- Реализовать Inbox в Payments Service.
- Реализовать Inbox в Orders Service для результатов оплаты.
- Проверить повторную доставку одного и того же события.
- Проверить, что повторный OrderPaymentRequested не списывает баланс второй раз.

Результат этапа: Система должна поддерживать сценарий

```
POST /orders
-> заказ PAYMENT_PENDING
-> событие OrderPaymentRequested
-> списание в Payments
-> событие OrderPaymentCompleted или OrderPaymentFailed
-> заказ PAID или PAYMENT_FAILED
```
